# 代码原则

AI 编写或修改代码时的行为约束 (非对话, 非文档格式).

## 编码前思考

不要假设. 不要隐藏困惑. 呈现权衡.

- 明确说明假设 — 如果不确定, 询问而不是猜测
- 呈现多种解释 — 当存在歧义时, 不要默默选择
- 适时提出异议 — 如果存在更简单的方法, 说出来
- 困惑时停下来 — 指出不清楚的地方并要求澄清

**检验标准**: 动手前所有假设和不确定点都已向用户说明并确认

## 改动范围

- 最小改动: 只改完成当前任务所必需的代码
- 不做无关重构, 不顺手整理未涉及的文件
- 聚焦的 diff 优于大范围重写
- 删除因你的改动而变得无用的导入, 变量, 函数; 不删除预先存在的死代码

**检验标准**: 每一行修改都能直接追溯到用户的请求

## 设计与复杂度

- **KISS**: 选最简单可行的方案, 不为"以后可能"加复杂度
- **DRY**: 重复逻辑提取共享抽象, 但不过早抽象 (两处相似不必立刻抽公共层)
- **YAGNI**: 不实现当前不需要的功能
- 区分根本复杂性 (问题固有) 与偶发复杂性 (方案引入); 持续削减后者
- 不要添加未要求的"灵活性"或"可配置性"
- 不要为不可能发生的场景做错误处理

**检验标准**: 资深工程师会觉得这过于复杂吗? 如果是, 简化

## 模块设计

- **SRP (单一职责)**: 一个类型或模块只有一个变化理由, 拆而不是堆
- **OCP (开闭)**: 对扩展开放, 对修改关闭; 新行为优先加代码, 少改稳定核心
- **LSP (里氏替换)**: 子类型可替换父类型; 不加强调用方没有的前置条件, 不削弱既有保证
- **ISP (接口隔离)**: 接口小而专一; 调用方只依赖它用到的能力
- **DIP (依赖反转)**: 依赖抽象, 不依赖具体实现
- **高内聚低耦合**: 模块内逻辑紧密相关; 跨模块通过窄接口交互, 避免直接依赖内部细节
- **最少惊讶 (POLA)**: API, 命名, 默认值符合直觉; 返回值与副作用和命名一致, 不做看起来只读其实有副作用的接口
- **Tell, Don't Ask**: 用方法表达行为, 少暴露内部状态让调用方在外部拼凑逻辑; 用访问控制封装边界

**检验标准**: 每个模块的职责可以用一句话说清楚

## 规模限制

- 单文件最大 800 行
- 单函数最大 50 行
- 最大嵌套 4 层

**检验标准**: 超过限制时先拆解再扩展, 不堆叠

## 遵循现有代码

- 动手前先读周边代码, 匹配命名, 类型, 错误处理, 目录结构
- 复用已有函数与组件, 不重新实现同类逻辑
- 新增代码应像同一作者写的

**检验标准**: 新增代码读起来像是该文件原有作者写的

## 注释

- 好代码应自解释; 只在非显而易见的业务逻辑或技术约束处加注释
- 不为显而易见的行为写注释

**检验标准**: 删掉所有注释后代码仍能被理解吗? 如果是, 注释不需要

## 错误处理

- 在系统边界验证输入
- 快速失败, 错误信息清晰
- 不静默吞掉错误

**检验标准**: 每个错误路径都有清晰的信息, 没有无处查找的静默失败

## 目标驱动执行

定义成功标准, 循环验证直到达成.

**优先使用 TDD (测试驱动开发)**:
- 先写测试, 再写实现, 最后重构 (Red-Green-Refactor)
- 写测试前先确认 seam (测试接缝): 明确哪个接口, 哪个边界, 不臆想 seam
- 测试通过前不进入下一功能

多步骤任务应分解为简短计划, 每步附带验证:

```
1. [步骤] -> 验证: [检查]
2. [步骤] -> 验证: [检查]
3. [步骤] -> 验证: [检查]
```

**检验标准**: 每个任务都有可验证的通过条件, 不依赖主观判断

## 如实说明

硬编码不等于糊弄. 代码里是什么, 对用户就说什么.

**通常可直接使用** (不必特别声明):

- 有明确语义的常量, 枚举, 协议字段, 算法参数
- 项目已有默认值, 或用户指定的固定值

**须在回复中主动说明** (不当作已完成的真实逻辑):

- 临时占位, 假数据, 未接通外部依赖的写死返回值
- 仅为走通路径的 stub, 或仍待接入配置, 环境, 真实数据源

**检验标准**: 用户能清楚区分哪些是真实的, 哪些是临时的
